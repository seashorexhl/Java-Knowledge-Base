# 11.序列化（条目85-90）

## 具体条目

    条目85：优先考虑替代方案
    在现代微服务架构中，永远优先使用 JSON 或 Protobuf。只有在维护老旧遗留系统时，才碰 Java 序列化。

    条目86：非常谨慎地实现 Serializable 
    实现 Serializable 会极大地增加类的维护成本。如果必须实现，一定要显式声明 serialVersionUID，
    否则只要改个字段名，旧版本保存的数据就再也无法反序列化了。敏感字段必须加 transient.

    条目87：考虑使用自定义的序列化形式
    默认的序列化会暴露类的内部实现细节。你应该只序列化“逻辑上必要”的数据。比如一个包含缓存的集合类，
    序列化时只需要写入原始数据，缓存应该在反序列化后重新计算。

    条目88：保护性地编写 readObject 方法 
    永远不要相信反序列化的输入！ 攻击者可以修改字节流。在 readObject 中，必须像对待外部网络请求一样，
    对所有参数进行校验，对可变对象进行防御性拷贝.

    条目89：对于实例控制，枚举类型优先于 readResolve 
    在 Java 5 之前，为了保证单例在序列化后不被破坏，必须写极其复杂的 readResolve() 方法。现在，
    只要是需要实例控制的类，直接用 Enum，JVM 在底层为你保驾护航。

    条目90：考虑使用序列化代理模式
    这是对付序列化攻击的“核武器”。通过 writeReplace() 和代理类，将反序列化的控制权从危险的真实类手中夺走，
    交给安全的代理类。即使真实类有漏洞，黑客也无法直接构造恶意对象。
