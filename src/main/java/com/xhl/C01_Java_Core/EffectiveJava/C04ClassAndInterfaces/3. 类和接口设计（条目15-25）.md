# 3. 类和接口设计（条目15-25）
    
## 具体条目

    条目15：最小化类和成员的可访问性
    能用 private 绝不用 protected。类、接口、方法的暴露范围越小，模块间的耦合度就越低。

    条目16：在公有类中，使用访问器方法，而不是用公有的字段
    公有字段会彻底暴露类的内部实现。一旦你以后想把 int age 改成 LocalDate birthDate，
    所有调用方都要跟着改。用 Getter/Setter 可以屏蔽这种变化。

    条目17：使可变性最小化
    不可变对象天生线程安全，可以作为 HashMap 的 Key。如果类必须是可变的，
    尽量让它的状态尽量少，方法尽量无副作用。    

    条目18：组合优先于继承
    继承打破了封装性（父类改了底层实现，子类可能直接崩溃）。优先把其他类当作组件“组装”起来，而不是“继承”下来。

    条目19：要么为继承而设计并提供文档说明，要么就禁止继承
    如果你非要允许别人继承你的类，必须在 Javadoc 里写清楚：哪些方法会被内部调用（Self-use）、
    重写它们会有什么副作用。如果懒得写，直接加 final。

    条目20：与抽象类相比，优先选择接口
    接口只用来定义“类型”（Type）。不要用它来导出常量（那是工具类的事），也不要滥用 default 
    方法（一旦发布，接口就永远被绑定了）。    

    条目21：为传诸后世而设计接口
    谨慎设计接口。        

    条目22：接口仅用于定义类型
    如果只是 导出常量，不应该使用接口

    条目23：优先使用层次结构而不是标记类
    看到 class Message { boolean isEmail; } 这种代码就要警惕。用多态和继承体系代替 
    if (msg.isEmail) 的判断逻辑。    

    条目24：与非静态成员类相比，优先选择静态成员类
    记住一个铁律——只要内部类不需要访问外部类的实例成员，必须加 static。不加 static 的内
    部类在序列化或内存管理时经常会引发隐蔽的 Bug。

    条目25：将源文件限制为单个顶层类
    保持源文件的整洁。如果一个文件里有多个顶层类，不仅影响编译，还会让代码审查者感到困惑。
