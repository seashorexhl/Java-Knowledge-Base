# 大型网站架构实战 Best Practices for Large-Scale Website Architecture 

## 1.大型网站业务和架构的发展

    A.业务演变
          静态网站 -> 动态网站 ->大型网站系统->云计算网站系统 -> 未来

    - 静态网站：早期HTML页面，内容固定，无用户交互。
    - 动态网站：引入数据库和服务器端脚本（如PHP），支持用户注册、评论等基础交互。
    - 大型网站系统：支持海量用户、高并发访问，具备复杂业务逻辑（如电商、社交）。
    - 云计算网站系统：基于云平台（如阿里云、AWS）实现弹性伸缩、自动化运维。
    - 未来：AI驱动的智能架构、边缘计算、Serverless普及。

    B.架构的发展
        动态网页时代 -> B/S 架构网站的崛起 -> CDN 加速网站相应 -> 应用和数据分离 -> 
    非关系型数据库和关系型数据库 -> 集群化 -> 分布式 -> 微服务 -> 未来

    - 动态网页时代：LAMP架构（Linux+Apache+MySQL+PHP）。
    - B/S架构崛起：浏览器/服务器模式取代C/S，降低客户端维护成本。
    - CDN加速：通过内容分发网络将静态资源就近分发，提升访问速度。
    - 应用与数据分离：应用服务器与数据库服务器独立部署，便于扩展。
    - 非关系型数据库与关系型数据库并存：Redis、MongoDB用于缓存和非结构化数据，MySQL用于事务处理。
    - 集群化：多台服务器组成集群，提升并发能力。
    - 分布式架构：服务与数据分布在不同节点，解决单点瓶颈。
    - 微服务架构：按业务拆分服务，独立开发、部署、扩展。
    - 未来：Service Mesh、无服务器架构（Serverless）、AI自动调优。

##  2.大型网站架构面临的挑战
    
    - 高并发：百万级QPS下如何保证响应速度。
    - 高可用：系统需7x24小时稳定运行，故障自动恢复。
    - 数据一致性：分布式环境下事务一致性（如CAP理论权衡）。
    - 可扩展性：业务增长时能否快速横向扩展。
    - 安全性：防DDoS、SQL注入、XSS等攻击。
    - 运维复杂度：微服务数量多，监控、日志、部署难度大。
    - 成本控制：资源利用率与成本之间的平衡。

##  3.前端架构

    - 前后端分离：前端使用React/Vue等框架独立开发，通过API与后端交互。
    - 组件化开发：UI拆分为可复用组件，提升开发效率。
    - 静态资源优化：
        - 懒加载：按需加载模块，减少首屏时间。
        - 预加载：预测用户行为，提前加载资源。
        - CDN加速：静态资源（JS/CSS/图片）通过CDN分发。
    - 缓存策略：
        - 浏览器缓存：设置Cache-Control、ETag。
        - Service Worker：离线缓存、资源拦截与降级。
    - 性能监控：使用Lighthouse、Web Vitals监控加载性能。

##  4.后端架构
    
    - 分层架构：
        - 表现层：处理HTTP请求（如Spring MVC）。
        - 业务逻辑层：核心业务处理（如Spring Boot）。
        - 数据访问层：ORM框架（如MyBatis）操作数据库。
    - 缓存机制：
        - 本地缓存：Guava Cache。
        - 分布式缓存：Redis缓存热点数据，减少数据库压力。
    - 异步处理：
        - 消息队列（如Kafka、RabbitMQ）处理邮件发送、日志记录等耗时操作。
    - 负载均衡：
        - Nginx、HAProxy将请求分发到多个应用服务器。
    - 数据库优化：
        - 读写分离：主库写，从库读。
        - 分库分表：按用户ID或时间分片。
        - 索引优化、SQL调优。

##  5.云计算服务架构

    - 弹性伸缩：根据流量自动增减云服务器（如阿里云ESS）。
    - 容器化部署：Docker + Kubernetes实现服务编排与自动扩缩容。
    - 云数据库：RDS（关系型）、MongoDB（文档型）、Redis（缓存）。
    - 云存储：OSS/S3存储图片、视频等大文件。
    - 云原生技术：
        - Service Mesh（如Istio）管理服务间通信。
        - Serverless（如函数计算）运行无状态函数。
    - 监控与日志：
        - 云监控、Prometheus + Grafana。
        - ELK（Elasticsearch + Logstash + Kibana）集中日志分析。

##  6.整体架构
    - 架构模式：微服务 + 分布式 + 云原生。
    - 核心组件：
        - API网关：统一入口，负责路由、鉴权、限流。
        - 服务注册与发现：Nacos、Eureka。
        - 配置中心：统一管理配置。
        - 熔断降级：Hystrix、Sentinel防止雪崩。
    - 数据流：
        - 用户请求 → CDN → 负载均衡 → API网关 → 微服务 → 数据库/缓存。
    - 高可用设计：
        - 多机房部署，异地容灾。
        - 数据库主从切换，自动故障转移。

##  7.单点登录架构设计
    - 目标：用户一次登录，访问所有子系统。
    - 技术方案：
        - 基于Token：用户登录后生成JWT，存储在Redis，各服务验证Token。
        - 基于Cookie + Redis：登录成功后生成Session ID，存入Redis，Cookie携带ID。
        - OAuth2.0：第三方登录（如微信、GitHub）。
    - 流程：
        1. 用户登录认证中心。
        2. 认证中心生成Token，返回给客户端。
        3. 客户端携带Token访问各服务。
        4. 服务验证Token有效性（调用认证中心或本地验证）。
    - 安全考虑：
        - Token加密、设置过期时间。
        - 防止Token泄露（HTTPS、HttpOnly Cookie）。

##  8.媒体管理系统架构设计
        
    - 功能：图片、视频上传、存储、转码、分发。
    - 架构：
        - 前端：支持拖拽上传、进度显示。
        - 后端：
            - 接收文件 → 消息队列（Kafka） → 转码服务（FFmpeg） → 存储到OSS。
        - 存储：
            - 原始文件：OSS/S3。
            - 缩略图/转码后文件：CDN加速访问。
        - 缓存：
            - Redis缓存元数据（文件名、URL、大小）。
    - 安全：
        - 文件类型校验、病毒扫描。
        - 访问权限控制（签名URL）。

##  9.直播系统架构设计
    
    - 核心流程：
        - 推流：主播通过RTMP推流到流媒体服务器（如SRS、NGINX-RTMP）。
        - 转码：转码服务将流转换为HLS/FLV格式，适配不同设备。
        - 分发：CDN分发直播流，降低延迟。
        - 拉流：观众通过HLS/FLV播放。
    - 架构组件：
        - 流媒体服务器集群：支持高并发推流。
        - 转码集群：GPU加速转码。
        - 消息队列：处理弹幕、礼物等实时消息。
        - 实时通信：WebSocket或WebRTC实现低延迟互动。
    - 优化：
        - 边缘节点推流，减少延迟。
        - 自适应码率：根据网络状况切换清晰度。
